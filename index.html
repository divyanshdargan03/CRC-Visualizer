Algorithm

Problem setup

  • Message bits: M (any format is first converted to binary).
  • Generator polynomial (binary): G, length m and degree m − 1.
  • Division is in GF(2): addition/subtraction is XOR; no carries.

Encoding (Sender)

  1. Convert input to binary: M.
  2. Pad with m − 1 zeros: P = M · 2m−1 (append m−1 zeros).
  3. Perform long division of P by G bit-by-bit:
    • Slide a window of size m from left to right.
    • If the window’s left bit is 1, XOR the window with G and write back.
    • If it is 0, just advance the window (no XOR).
  4. The final m − 1 bits are the remainder R (the CRC).
  5. Encoded message: M || R.
Pseudocode (bitwise division) 
input: M (binary string), G (binary string), m = len(G)
# pad
P = M + "0" * (m-1)
W = list(P)  # mutable working array
for i in range(0, len(P) - m + 1):
    if W[i] == '1':
        for j in range(0, m):
            W[i+j] = '0' if (W[i+j] == G[j]) else '1'  # XOR
# remainder is last m-1 bits
R = ''.join(W[len(P)-(m-1):])
encoded = M + R

Verification (Receiver)

  1. Receive M' = M || R and choose G (defaults to the sender’s choice here).
  2. Run the same division on M' by G.
  3. If the final remainder is all zeros, the frame is considered valid; otherwise an error is detected.

Notes and edge cases

  • All-zero message: still yields a deterministic CRC based on G.
  • Leading zeros in M are preserved; division is positional.
  • Custom polynomials should be binary and start with 1 to define degree m−1.
  • Time complexity is O(n · m), for message length n and polynomial length m.

Working Principle

CRC as polynomial arithmetic over GF(2)

A binary string (e.g., 11001) is viewed as a polynomial with coefficients in GF(2), e.g., 1·x⁴ + 1·x³ + 0·x² + 0·x + 1. The generator G is also a polynomial whose highest coefficient is 1 (so its degree is well-defined).

Division is standard long division but with XOR as add/subtract. There are no carries in GF(2). Each time the current window’s leading bit is 1, we XOR the window with the generator. When it’s 0, we just advance to the next position. Our visualizer shows this as “window → generator → underline → XOR result”, aligned under the dividend.

Why append zeros before division?

Appending m−1 zeros is equivalent to multiplying the message polynomial by xm−1, reserving space for the remainder produced by the division. The remainder bits overwrite these zeros and become the CRC appended at the sender.

Sender/Receiver symmetry

  • Sender: computes remainder R from M·xm−1 ÷ G, transmits M || R.
  • Receiver: divides M || R by the same G. If the remainder is all zeros, the frame passes; otherwise it’s flagged.

Error detection intuition

If noise flips some bits producing error polynomial E(x), the received polynomial becomes M(x)·xm−1 + R(x) + E(x). By construction, M(x)·xm−1 + R(x) is divisible by G(x), so the receiver’s remainder equals E(x) mod G(x). Well-chosen standard polynomials detect many common error patterns (all single-bit errors, most short burst errors, and more).

Limitations

  • CRC provides integrity, not authenticity; it is not a cryptographic MAC.
  • Some rare error patterns are undetected depending on G; standards choose G to minimize these.

Learn

Materials (selected notes — from Philip Koopman)

The following concise notes summarize practical CRC guidance adapted from Philip Koopman's material on checksums and CRCs. These are presented as a quick reference for students using the visualizer:

  • Purpose: CRCs are lightweight error-detection codes designed to detect common transmission faults (single-bit errors, most small burst errors, and many patterns of multiple-bit errors) using polynomial arithmetic over GF(2).
  • How they work (high level): Treat a binary message as a polynomial, multiply by x^(m-1) (append m−1 zeros), divide by the generator polynomial G(x) using XOR (no carries). The remainder (m−1 bits) is appended as the CRC. The receiver performs the same division; a zero remainder indicates no detected error.
  • Polynomial selection: Choosing G(x) is critical — well-known polynomials (CRC-16, CRC-32) are selected for strong detection of typical error patterns. Koopman highlights that some polynomials are better at detecting particular kinds of burst errors and recommends selecting a polynomial that matches the expected error model.
  • Burst error detection: A generator of degree m−1 will detect all burst errors of length less than m, with diminishing guarantees for longer bursts depending on the polynomial.
  • Limitations: CRCs detect accidental corruption well but do not provide cryptographic integrity or protection against intentional tampering—use cryptographic MACs for that purpose.
  • Implementation notes: CRC computation can be implemented as bitwise division or optimized with lookup tables (byte-wise) or hardware shift-registers; Koopman discusses trade-offs between speed, table size, and implementation platform constraints.
  • Practical tip: Always document the polynomial (binary and mathematical form), initial/final XOR values, and bit-ordering (LSB/MSB) when sharing CRC-encoded data — mismatches in conventions are a common interoperability source of errors.

Help

Overview

This visualizer helps you learn and experiment with Cyclic Redundancy Checks (CRC). It converts your input to binary, computes a CRC using a chosen generator polynomial, and shows the long-division steps used to compute the remainder. Use the mode selector to switch between encoding (Sender) and verification (Receiver).

How to provide input

Choose the input format from the "Input Format" dropdown (Binary, Decimal, Hexadecimal, ASCII, or Text). Then enter the value in the input box. The visualizer will convert the value to binary before computing the CRC. For Receiver mode, paste the full encoded binary message (message + CRC).

How to run the visualizer

1) Select a generator polynomial (standard options like CRC-8, CRC-16, CRC-32 or choose Custom and supply a binary polynomial). 2) Choose Mode: Sender to compute and append the CRC, or Receiver to verify an encoded message. 3) Click Calculate CRC. Results, division steps and the final remainder appear below.

Recommended workflow

  • • In Sender mode: enter the original data, pick a polynomial, calculate, then copy/save the encoded message.
  • • Optionally use "Simulate Error" to flip bits in the encoded message and observe detection behavior.
  • • In Receiver mode: paste the encoded message (message + CRC) and calculate to check whether the remainder is all zeros.

What is processed

The tool converts your input to a binary string, appends m−1 zeros (where m is the polynomial length), and performs bitwise division by the generator polynomial using XOR (no carries). The remainder (the last m−1 bits) is the CRC.

Interpreting results and visualization

The long-division visualization shows each XOR operation window, the divisor alignment, and the evolving working array until the final remainder is produced. In Receiver mode, an all-zero remainder means no error detected; a non-zero remainder indicates detected corruption. Use the "Final Result" and the remainder line to make this judgment.
